# 视频发现与筛选设计（Question → Video Set）

> 在现有链路前增加一环：**用户提出问题 → 自动搜集相关视频 → 选出一组值得解析的视频 → 进入原有解析/研报链路**。
> 本文只回答一个问题：当搜索结果很多时，**选多少、选哪些、为什么选它们**。
>
> 更新：评分权重、自动排序倾向与资格门的最新设计见
> [`Discovery与检索排序设计.md`](Discovery与检索排序设计.md)。本文保留早期方案与历史调参记录。

---

## 一、为什么需要这一环

现有 Gether 的输入是“用户指定的一组视频”。真实用户更自然的入口是：

> “帮我研究一下 2026 年 AI 编程工具的真实落地情况，找出不同公司/不同立场的人怎么说。”

这时系统需要先完成：

1. 把问题拆成可检索的意图与子问题；
2. 在 B站 / YouTube 搜索候选视频；
3. 从几十上百个结果中选出 3–6 个真正值得解析的视频；
4. 解释选择理由，并允许用户干预；
5. 再进入 ASR/OCR → 证据 → 混合检索 → 研报。

**这一环的难点不是“搜到视频”，而是“在有限预算下选出覆盖问题、立场多元、信息密度高的视频集合”。**

---

## 二、目标与边界

### 2.1 目标

- 输入自然语言问题，输出一组**可解释的视频集合**。
- 控制视频数量与总时长，避免解析成本失控。
- 保证覆盖面：问题的每个子主题至少有一个视频。
- 保证多样性：不同来源、不同作者、不同立场，避免同质化。
- 为冲突裁决服务：主动寻找“反方/风险/失败案例”，而不是只找赞同观点。
- 支持 Human-in-the-loop：用户可增删、替换、确认。

### 2.2 不做

- 不做全网爬虫；只使用平台搜索/公开 API。
- 不下载未选中的视频；候选阶段只取元数据。
- 不在发现阶段做完整 ASR/OCR；最多取标题、简介、标签、搜索片段。
- 不承诺“找到唯一正确答案”；目标是找到足够支撑研报的证据集合。

## 三、全链路位置

```text
用户问题
   ↓
① Query Planning（意图 / 子问题 / 检索词）
   ↓
② Search（B站 / YouTube，多 query、多页）
   ↓
③ Candidate Pool（去重、粗过滤、元数据补全）
   ↓
④ Ranking（相关性 / 权威 / 新鲜 / 多样性 / 成本）
   ↓
⑤ Selection（动态数量 + 覆盖约束 + MMR + 时长预算）
   ↓
⑥ Sufficiency Check（不够则放宽/HITL）
   ↓
⑦ HITL 确认（可选）
   ↓
VideoRef 集合
   ↓
原有链路：解析 → 证据 → 索引 → LangGraph 研报 → 冲突裁决
```

## 四、Query Planning：把问题变成可检索的意图

### 4.0 先重写问题

在检索前，先把用户问题重写为适合平台搜索与向量匹配的查询：

```json
{
  "rewritten": "人生第一辆车 二手车还是新车 优缺点 成本 风险 真实体验",
  "keywords": ["第一辆车", "二手车", "新车", "成本", "风险"],
  "intent": "decision",
  "must_have": ["成本", "风险"],
  "avoid": ["教程", "验车", "检测", "选购", "砍价"]
}
```

- 决策型问题必须改写成“对比/取舍”查询，而不是“如何验车”；
- `avoid` 会并入 discovery 的 negative_terms；
- 重写失败时有规则兜底，不会阻塞检索。

使用 LLM 输出结构化检索计划：

```json
{
  "intent": "评估 AI 编程工具的真实落地情况",
  "entities": ["Cursor", "Copilot", "Claude Code", "企业研发团队"],
  "facets": [
    {"id": "f1", "label": "效率提升", "query": "AI 编程工具 效率 提升 实测", "stance": "positive"},
    {"id": "f2", "label": "代码质量风险", "query": "AI 编程 代码质量 缺陷 风险", "stance": "negative"},
    {"id": "f3", "label": "企业落地", "query": "企业 研发团队 AI 编程 落地 经验", "stance": "neutral"},
    {"id": "f4", "label": "反方/失败案例", "query": "AI 编程工具 翻车 失败 案例", "stance": "negative"}
  ],
  "negative_terms": ["直播", "切片", "搬运", "广告"]
}
```

规则：

- 3–6 个 facet；每个 facet 生成 1–2 个检索 query（中文 + 英文/同义词）。
- 评估型问题强制包含 **反方/风险/失败案例** facet，服务后续冲突裁决。
- 生成 `negative_terms`，用于搜索后过滤标题党、搬运、直播回放。
- 用问题中的实体做 query 变体：品牌名、产品名、公司名、人名。

## 五、Search：候选池怎么来

### 5.1 搜索入口

| 来源 | 方式 | 说明 |
|---|---|---|
| B站 | `bilisearch` / 搜索 API | 当前网络可用；需要 cookies 时走 `BILIBILI_COOKIES_FILE` |
| YouTube | `ytsearch` | 当前网络不可达；配置 `YTDLP_PROXY` 后启用 |

### 5.2 抓取预算

| 参数 | 默认 | 说明 |
|---|---|---|
| 每个 query 抓取 | 20 条 | 先取第 1 页，必要时第 2 页 |
| 总 query 数 | 6–10 | facet 数 × 1–2 |
| 原始候选 | 100–150 | 去重前 |
| 去重后候选池 | 40–80 | 进入排序 |
| 元数据补全 | Top 30 | 只对高潜候选调用详情接口 |

### 5.3 去重与粗过滤

去重：

- `source + source_video_id` 完全一致；
- 规范化标题 hash（去标点/空格/emoji）；
- 标题 + 简介 embedding 相似度 > 0.9 聚为一簇，保留分数最高的代表；
- 同作者、同系列（标题前缀相同）只保留最佳 1–2 条。

粗过滤：

- 排除直播、预告、纯音乐、播放列表、付费/会员专享；
- 时长：默认 3–180 分钟；优先 8–45 分钟；
- 语言：中文优先，英文可接受；
- 标题党/搬运/切片：命中 `negative_terms` 扣分或剔除；
- 发布时间：可选时间窗；无日期不直接剔除，但新鲜度得分低。

### 5.4 播放量硬过滤与回退

「只看播放量 > 1 万」是合理的默认起点，但**不能做成没有回退的硬阈值**，否则 niche 领域的专家访谈、新发布的高质量视频会被全部过滤掉。

默认策略：

```text
min_views = 10,000
fallback_min_views = 1,000

candidates = 播放量 >= min_views
if len(candidates) < min_videos:
    candidates = 播放量 >= fallback_min_views
    warning("高质量候选不足，已降低播放量门槛")
if len(candidates) < min_videos:
    candidates = 全部候选（仅去重/粗过滤）
    warning("播放量门槛已关闭，请人工复核")
```

例外保留（即使播放量低于门槛也进入排序）：

- **至少覆盖 2 个 facet**（避免单个关键词误命中）；
- 平台认证作者 / 官方机构 / 高校实验室；
- 互动率（点赞/播放、投币/播放）位于候选池 Top 20%；
- 发布时间 ≤ 30 天且作者权威度位于 Top 20%；
- 用户显式指定的视频 / 频道。

其他规则：

- 播放量缺失：不直接剔除，进入“待定”并扣分，等待元数据补全；
- `DISCOVERY_MIN_VIEWS` 在 Topic Gate、排序、coverage 选择之前执行硬过滤；
- 已知低于阈值或播放量未知的候选都不进入候选池；
- B站与 YouTube 仍各自保留 `BILIBILI_MIN_VIEWS` / `YOUTUBE_MIN_VIEWS` 作为低播放软信号；
- 播放量不进入“相关性”分；过滤统计写入 `sufficiency.filter.min_views`；
- 过滤日志记录：过滤前数量、阈值、保留数量、被过滤数量，便于解释与调参。

推荐参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `DISCOVERY_MIN_VIEWS` | `8000` | 全局硬过滤下限，排序前执行 |
| `BILIBILI_MIN_VIEWS` | `10000` | B站低播放软信号/例外上限 |
| `YOUTUBE_MIN_VIEWS` | `10000` | YouTube 低播放软信号/例外上限 |
| `DISCOVERY_FALLBACK_MIN_VIEWS` | `1000` | 候选不足时回退配置（预留） |
| `DISCOVERY_MIN_VIEWS_EXCEPTION` | `true` | 认证/高互动/新发布例外（预留） |
| `DISCOVERY_MIN_ENGAGEMENT_RATE` | `0.01` | 例外所需最低互动率（预留） |

### 5.5 搜索退避与 query 间隔

B站搜索在短时间内多次请求会触发 412。MVP 策略：

```text
retries = 3
backoff = 4s, 8s（指数退避）
query interval = 2s
```

- 仅对 412 / 429 / 超时 / 连接错误重试；
- 每次 query 之间固定间隔，避免连续打满；
- 单个 query 最终失败时记录 warning，继续其他 query；
- 所有 query 都失败才返回“未搜索到候选”。

## 六、Ranking：单个视频的分数

### 6.1 相关性 `rel`

```text
rel = 0.5 * BM25(rewritten_query, title + desc + tags)
    + 0.5 * cosine(embed(rewritten_query), embed(title))
```

- 用户问题先重写，再用重写后的 query 做 BM25 与向量匹配；
- **向量只匹配视频标题**，简介只参与 BM25，避免简介噪声主导语义分；
- 搜索 query 同时包含重写 query 与 facet query。

- BM25 负责精确实体/术语；
- Embedding 负责语义改写与同义表达；
- 若有搜索片段（snippet），拼进文本一起算。
- 多 facet 时：`rel = max(facet_rel)` + `0.2 * mean(top2 facet_rel)`，避免单 query 偏差。

### 6.2 权威度 `auth`

优先使用平台公开信号，并在候选池内做百分位归一化：

| 信号 | B站 | YouTube |
|---|---|---|
| 作者 | 粉丝数、认证 | 订阅数、认证 |
| 内容 | 播放、点赞、投币、收藏 | 播放、点赞、评论 |
| 互动率 | 点赞/播放、投币/播放 | 点赞/播放 |

避免直接用绝对播放量（大账号碾压小账号）；使用 `log1p` 后按候选池百分位归一化。

### 6.3 时效性 `fresh`

```text
age_days = (now - published_at) / 86400
fresh = exp(-age_days / half_life)
```

- 默认 `half_life = 180` 天，可通过 `DISCOVERY_FRESHNESS_HALF_LIFE_DAYS` 调整；
- 权重 `DISCOVERY_FRESHNESS_WEIGHT=0.15`；
- 可选硬过滤 `DISCOVERY_MAX_AGE_DAYS`，默认 `0`（关闭）；开启后优先保留时间窗内视频，候选不足时回退并告警；
- 无发布时间：`fresh = 0.5`（中性），并在前端显示“发布时间未知”。

### 6.4 时长惩罚 `dur_pen`

```text
dur_pen = 0                 if 8min <= duration <= 45min
        = (8 - minutes) / 8 if duration < 8min
        = (minutes - 45) / 45 if duration > 45min
```

长视频解析成本高，但不直接排除；用惩罚而不是硬阈值。

### 6.5 冗余惩罚 `red`

- 与已选视频的标题/简介 embedding 最大相似度 `sim_max`；
- `red = max(0, sim_max - 0.75) / 0.25`；
- 同作者/同系列额外 +0.1。

### 6.6 综合分

用于**初排**：

```text
base = 0.55 * rel
     + 0.15 * auth
     + 0.15 * fresh
     + 0.05 * source_diversity
     - 0.10 * dur_pen
```

选择阶段再加入覆盖与冗余：

```text
select_score = 0.45 * rel
             + 0.15 * auth
             + 0.10 * fresh
             + 0.20 * facet_coverage
             + 0.10 * debate_coverage
             - 0.15 * redundancy
             - 0.05 * dur_pen
```

所有权重可配置，后续用评测集调参。

### 6.7 facet 匹配阈值

facet 是否命中由两路分数决定：

```text
facet_score = lexical_weight * BM25_norm
            + embedding_weight * embedding_sim
命中：facet_score >= facet_match_threshold
```

默认 `threshold=0.55`、`lexical=0.5`、`embedding=0.5`。

- 阈值过低：PPT/泛科普视频因单个关键词误命中（首轮实机就出现过）；
- 阈值过高：垂直领域视频被漏掉；
- 需要按问题类型/评测集标定，而不是全局固定。

首轮标定结果（1 个问题、30 候选、手动标签）：

| threshold | selected | precision | recall |
|---:|---:|---:|---:|
| 0.50 | 4 | 1.00 | 0.6667 |
| 0.55 | 4 | 1.00 | 0.6667 |
| 0.60 | 4 | 0.75 | 0.5000 |
| 0.65 | 4 | 0.75 | 0.3333 |
| 0.75 | 4 | 0.75 | 0.3333 |

结论：

- 单靠阈值无法区分“教程”和“实测/研究”；
- 加入 **negative_terms + 多标签 content_type + 教程/求职类过滤** 后：
  - precision 从 0 → **1.0**；
  - recall 从 0 → **0.667**；
  - 阈值 0.55 是当前最佳平衡点（0.6 开始 coverage 下降）。
- 仍有 2 条相关视频未选中：一条 633 播放（低播放门槛），一条 1,909 播放（低播放例外条件不足）；下一步优化低播放证据型内容的例外策略，而不是继续放宽阈值。

已实现：

- planner 输出 `negative_terms`；
- 多标签 `content_types`：教程 / 研究 / 体验 / 观点 / 新闻 / 求职 / 其他；
- 评估型问题下，教程/求职类降权；
- 非教程证据型候选足够时，硬过滤教程/求职类；
- 前端展示 content_type 与负向词。

参数：

| 参数 | 默认 |
|---|---|
| `DISCOVERY_FACET_MATCH_THRESHOLD` | 0.55 |
| `DISCOVERY_FACET_LEXICAL_WEIGHT` | 0.5 |
| `DISCOVERY_FACET_EMBEDDING_WEIGHT` | 0.5 |

## 七、Selection：选多少、选哪些

### 7.1 视频数量

不要固定“每次 5 个”，而是动态计算：

```text
facets = 3..6
n_min = 2
n_max = min(8, floor(duration_budget_min / avg_candidate_duration))
n_target = clamp(ceil(1.5 * facets), n_min, n_max)
```

默认：

| 参数 | 默认 |
|---|---|
| `max_videos` | 5 |
| `min_videos` | 2 |
| `hard_max_videos` | 8 |
| `duration_budget_min` | 120 分钟 |
| 目标平均时长 | 15–30 分钟 |

停止条件（满足任一）：

1. 已选数量达到 `n_target`；
2. 新增视频的边际 facet 覆盖增益 < 10%；
3. 总时长达到预算；
4. 下一个候选的 `select_score` 低于阈值（如 0.30）。

### 7.2 选择算法：Coverage-aware MMR

```text
1. 从候选池取 Top 30（按 base 分）。
2. 按主题 embedding 聚类，每簇保留代表。
3. 先为每个 facet 选 1 个最佳候选（保证覆盖）。
4. 剩余名额用 MMR 填充：
   mmr = λ * rel - (1-λ) * max_similarity_to_selected + coverage_bonus
   λ = 0.7
5. 若存在“反方/风险”facet，强制至少选 1 条匹配该 facet 的视频。
6. 检查来源多样性：若两个来源都可用，尽量各至少 1 条。
```

### 7.3 去重与冲突准备

- 同主题只保留 1–2 条代表，避免 5 个视频说同一句话；
- 保留至少 2 个不同作者/不同立场，服务后续冲突裁决；
- 记录每个视频匹配的 facet 和选择理由，供前端展示与人工调整。

### 7.4 输出

```json
{
  "session_id": "...",
  "question": "...",
  "facets": [...],
  "selected": [
    {
      "source": "bilibili",
      "source_video_id": "BV...",
      "title": "...",
      "duration_ms": 1800000,
      "score": 0.82,
      "matched_facets": ["f1", "f3"],
      "reason": "覆盖效率提升，作者为一线研发团队，时效性高",
      "cluster_id": "c3"
    }
  ],
  "rejected_top": [
    {"title": "...", "reason": "与已选视频高度重复"}
  ],
  "sufficiency": {"ok": true, "coverage": 0.83, "warnings": []}
}
```

## 八、充分性判断与 HITL

### 8.1 充分性

满足以下条件才自动继续：

- 已选视频 ≥ 2；
- facet 覆盖率 ≥ 0.6；
- Top 候选相关性 ≥ 0.35；
- 至少 1 个反方/风险 facet（若问题为评估型）。

否则：

- 自动放宽：减少 `negative_terms`、增加同义词、放宽时间窗；
- 仍不足：返回 `insufficient`，建议用户改问题或上传指定视频；
- 不静默用低质量视频凑数。

### 8.2 Human-in-the-loop

前端展示：

- 每个视频的标题、作者、时长、匹配 facet、选择理由；
- 被拒绝的 Top 候选及原因；
- 用户可删除、替换、手动粘贴视频链接；
- 确认后创建解析任务。

默认建议开启确认；熟练用户可开启“自动选择”。

## 十、评测方案

### 10.1 数据集

- 20 个研究问题，覆盖科技/产品/行业/人物；
- 每个问题人工标注 5–10 个相关视频（含至少 1 个反方）；
- 记录视频的 facet 标签与相关性等级（0/1/2）。

### 10.2 指标

| 指标 | 说明 |
|---|---|
| `Recall@20` | 候选池是否召回相关视频 |
| `nDCG@10` | 候选排序质量 |
| `Selection Precision` | 选中视频中相关视频比例 |
| `Facet Coverage` | 选中集合覆盖的 facet 比例 |
| `Stance Diversity` | 正/反/中立立场覆盖 |
| `Duplicate Rate` | 选中集合内高相似视频比例 |
| `Total Duration` | 解析成本代理指标 |
| `End-to-End Report Gain` | 有/无发现阶段的研报人工评分对比 |

### 10.3 对照实验

1. 仅 BM25；
2. BM25 + Embedding；
3. + 权威/新鲜度；
4. + MMR 多样性；
5. + facet coverage / 反方约束。

用同一批问题比较 Selection Precision、Coverage、Duration 和人工评分。

播放量阈值对照：`0 / 1k / 10k / 50k`，观察 Recall 损失、候选池规模和最终 Selection Precision。

## 十一、风险与应对

| 风险 | 应对 |
|---|---|
| 搜索结果被标题党污染 | 负向词、权威度、时长/来源惩罚 |
| 播放量硬阈值误杀 niche 优质视频 | 1,000 回退 + 认证/高互动/新发布例外 + 人工复核 |
| 播放量刷量 | 互动率、作者权威、多信号交叉验证 |
| 平台风控/搜索不可用 | 缓存、限速、cookies、代理；B站优先；412 指数退避 + query 间隔 |
| YouTube 网络不可达 | 可配置代理；不可用时降级为 B站-only |
| 选太多导致解析成本爆炸 | 动态数量 + 时长预算 + 边际覆盖停止 |
| 选太少导致研报片面 | 最小 2 条 + facet 覆盖 + 反方约束 |
| 同质化严重 | 聚类去重 + MMR + 来源多样性 |
| 排序过拟合 | 权重配置化，离线评测 + 线上反馈 |
| 版权/合规 | 只取元数据与用户确认后的视频；不批量下载未选内容 |

## 十二、分阶段实现

### P2.6（MVP）

- B站-only 搜索；
- LLM query/facet 规划；
- 元数据排序 + 去重 + 动态数量 + 基础 MMR；
- `POST /internal/discovery/sessions` + `confirm`；
- 评测集 20 问题，输出 Selection Precision / Coverage。

### P2.7

- YouTube（代理可用时）+ 来源多样性；
- 搜索片段/简介 embedding 重排；
- 缓存与限速；
- HITL 前端交互。

### P3+

- 与 LangGraph/SSE 对接；
- 用户反馈学习排序权重；
- 可选“仅搜索不解析”的快速模式。

## 十三、面试叙事

> “Gether 不只是把用户给的视频做成研报。它会先把一个研究问题拆成多个子问题，在 B站/YouTube 上多路检索，再用相关性、权威度、时效性、主题覆盖和立场多样性做排序，在时长预算内选出一组互相补充、允许用户干预的视频集合。这样后面的证据链和冲突裁决才有意义——因为输入本身就不是同质化的五个视频。”

## 十四、默认参数速查

| 参数 | 默认 |
|---|---|
| facet 数 | 3–6 |
| 每 facet query | 1–2 |
| 每 query 抓取 | 20 |

| 时效半衰期 | 180 天 |
| 时效权重 | 0.15 |
| 最大视频年龄 | 0（关闭） |
| 聚类阈值 | 0.90 |
| MMR λ | 0.7 |
| facet 覆盖下限 | 0.6 |
| 边际覆盖停止 | 10% |

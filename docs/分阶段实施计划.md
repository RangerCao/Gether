# Gether 分阶段实施计划

> 配套文档：[项目架构选型说明](./项目架构选型说明：Java%20+%20FastAPI%20双栈架构设计.md) · [竞品分析](./竞品分析.md) · [配置与技术选型](./配置与技术选型.md)
>
> 一句话目标：**用一条可演示的垂直链路，把“多源视频 → 多模态证据 → 冲突裁决 → 可溯源研报”跑通，并用真实指标支撑简历叙事。**

---

## 一、成功标准（先定义“做完”）

项目不以“代码写完”为完成，而以下面三条同时满足为完成：

1. **可演示**：10 分钟内，从粘贴 2 个视频链接开始，到产出一份带可点击时间戳引用的研报，中途可修改大纲、可看到冲突卡片，全程无需手动改数据库。
2. **可解释**：每条结论都能回溯到 `video_id + 起止时间戳 + 模态来源（ASR/OCR）`；冲突不是 LLM 随口说的，而是 Evidence Ledger 中 support relation 的显式结果。
3. **可量化**：至少产出 5 个可写进简历的数字（见第九节），且每个数字都有可复现的脚本。

### Demo 脚本（验收时照此走）

| 步骤 | 用户动作 | 期望表现 |
|---|---|---|
| 1 | 粘贴 2 个同主题视频链接，提交 | 立即返回 TaskID，页面进入生成中，SSE 已连接 |
| 2 | 等待解析 | 左栏实时显示 `PARSING → PLANNING`，展示 ASR/OCR 进度与证据包数量 |
| 3 | 大纲返回 | 右栏出现可编辑大纲，任务暂停在 `PLANNING`，等待确认 |
| 4 | 修改一个章节标题并确认 | 状态转 `GENERATING`，流式输出正文 |
| 5 | 点击任意引用角标 | 播放器跳到对应秒数，高亮证据原文与模态来源 |
| 6 | 打开冲突面板 | 看到至少 1 组 claim 级冲突：两种说法、各自证据包、qualifier 差异 |
| 7 | 生成结束 | 状态 `DONE`，SSE 关闭，可导出 Markdown |

## 二、实施总策略

- **垂直切片优先**：不按“先把 Java 写完，再写 Python，再写前端”推进，而是每个阶段都交付一条能跑的链路。
- **先真后全**：核心差异点（证据包、claim 级冲突、时间戳溯源、HITL）必须真做；RAPTOR 多层树、完整鉴权、熔断降级可以第二批加固。
- **接口先定**：P0 就冻结 SSE 事件协议、任务状态枚举、Evidence Packet / Claim / Ledger 三张表结构，避免后期返工。
- **可回退**：每个外部依赖（LLM、ASR、OCR、向量库）都走适配器接口，任何一家挂掉都能降级或替换；LLM 至少支持 DeepSeek 与 DashScope 一键切换。
- **指标先行**：P1 开始就埋点（耗时、token、证据数、引用校验通过率），不要等最后补。

## 五、各阶段详细拆解

### P0 骨架与环境（2 人日）

**目标**：任何人 clone 后两条命令能起完整依赖，且核心协议不再变动。

**任务**
- [ ] `git init`、`.gitignore`（排除 `.env`、`secrets/`、`data/`、`models/`、`*.wav`、`frames/`）
- [ ] `infra/docker-compose.yml`：Postgres 16 + pgvector、MinIO、Redis（可选）
- [ ] `initdb/`：创建 `vector` 扩展、核心表、索引
- [ ] Python：`pyproject.toml`（uv/poetry 任选）、`pydantic-settings` 配置加载、结构化日志（含 `trace_id`）
- [ ] Java：Spring Boot 3.x + JDK 21 骨架，`/actuator/health`
- [ ] Web：Vite + React + TS 骨架，能调通一个健康接口
- [ ] `Makefile`：`up` / `down` / `migrate` / `test` / `smoke`
- [ ] 冻结三份协议文档（可直接写进 `docs/protocol.md`）：
  - 任务状态枚举：`PENDING → PARSING → PLANNING → GENERATING → DONE / FAILED / CANCELLED`
  - SSE 事件类型：`state` / `progress` / `outline` / `token` / `citation` / `conflict` / `heartbeat` / `error` / `done`
  - 数据契约：`EvidencePacket` / `Claim` / `LedgerEntry`（字段见 P1、P3）
- [ ] LLM 供应商注册表：`LLM_PROVIDER` 至少支持 `deepseek` / `dashscope`（另留 `mock`）；角色 → 模型解析顺序固定；未启用供应商不校验 key
- [ ] 视频源适配器契约：`bilibili` / `youtube` 统一输出 `VideoRef`，本地上传只作为 Demo fixture
- [ ] CI：ruff + pytest + eslint + `mvn -q test`

**验收**
- `make up && make smoke` 全绿；三个服务健康检查通过。
- 故意填错一个必填环境变量，服务启动时**快速失败**并打印缺失项（不要求读代码排查）。
- 在 `deepseek` 与 `dashscope` 之间切换，只改 `.env` 并重启，`make smoke` 均通过（无 key 时用 `LLM_PROVIDER=mock` 验证）。

### P1 多模态解析与证据包（5 人日）

**目标**：把 2 个视频变成结构化、可溯源、模态完整的证据集合。

**任务**
- [x] 视频源适配器：`bilibili`（`BV/av/ep/b23.tv`、多 P）与 `youtube`（`watch/youtu.be/shorts`）各自实现 `VideoSource`，统一输出 `VideoRef`；拒绝播放列表、直播、超时长输入
- [x] 分源配置：B站/YouTube 独立 cookies、字幕语言优先级、抽帧清晰度上限（见配置文档 2.7）
- [x] 下载适配器（yt-dlp）：字幕优先 → 音频 → 限速/并发/超时/清理；支持本地 fixture
- [x] 语音轨：原生字幕（VTT/SRT）解析；无字幕走 faster-whisper 适配器（词级时间戳）
- [x] 视觉轨：关键帧抽取（场景切换 + 固定间隔兜底）、RapidOCR / PaddleOCR 适配器
- [x] 时间轴对齐：OCR 文本按帧时间归并为区间证据；与 ASR 片段共用统一时间基准（毫秒）
- [x] Evidence Packet 落库：`evidence_id / video_id / modality / text / start_ms / end_ms / frame_ref / confidence / source_type / content_hash`
- [x] MinIO 存储：关键帧上传与降级（S3 兼容服务联调通过）
- [x] 解析进度上报：按阶段更新任务进度（SSE/Java 回调待 P4）
- [x] 单测：字幕/ASR/OCR 三条路径均有 fixture；YouTube 因网络不可达仅做适配器与 fixture 测试

> 当前状态：B站 3 个短视频共 **126 条证据**（66 ASR + 60 OCR）落库成功；
> 33 分钟长视频用 `base` + `beam_size=1` 产出 **1009 条 ASR 证据**，耗时约 4.3 分钟（CPU）；
> MinIO 通过 S3 兼容服务联调通过。YouTube 在当前网络环境不可达，仅通过适配器单测与 fixture 验证。

**验收**
- B站与 YouTube 各 1 个视频（总时长 ≥ 40 分钟）解析成功率 100%，每个视频产出 ≥ 100 条证据包。
- 两个源产出同构的 `EvidencePacket`，下游代码无需按来源分支。
- 随机抽 20 条引用人工核对，时间戳误差 ≤ 2 秒。
- 有原生字幕时**不触发** ASR（日志可证），节省算力。
- 同一视频重复解析，`content_hash` 去重后证据数不翻倍。

**风险**：B站风控 412、YouTube 机器人校验、无 GPU 时 ASR 过慢。应对见配置文档“降级矩阵”。

### P2 索引与混合检索（3 人日）

**目标**：给定一个章节问题，能召回跨视频、跨模态的相关证据，且延迟可控。

**任务**
- [x] 分块策略：按字符目标 360 / 上限 480 / 重叠 60 聚合证据；长证据按时间比例切分
- [x] Embedding：`bge-small-zh-v1.5`（512 维）批量向量化、归一化、写入 pgvector + HNSW
- [x] BM25：jieba 中文分词 + 进程内 `rank_bm25`；检索时按任务重建
- [x] RRF 融合：`score = Σ w_i/(k + rank)`；调参后 `k=40`、向量/BM25 权重 1:1
- [x] 检索接口：`POST /internal/retrieve`、`POST /internal/tasks/{id}/index`、`GET /chunks`
- [ ] （P2b，可选）RAPTOR：聚类 → 多层摘要 → 摘要节点也可被检索；**不阻塞主线**
- [x] 埋点：网格搜索脚本输出 Recall@10 / MRR / nDCG@10 / 分块参数
- [x] 过滤：`video_id / modality / 时间范围` 已接入检索 API
- [x] 万级证据压测：10k chunks，P95 = 296.4ms

> 当前调参结果（30 条人工 query，bge-small-zh-v1.5，18 个 chunk）：
> 混合检索 Recall@10 **0.9284** / nDCG@10 **0.8673** / MRR **0.8931**；
> 向量单路 0.9110 / 0.8090 / 0.8236；BM25 单路 0.8915 / 0.7930 / 0.8250。
> 分块 360/480/60、RRF k=40、权重 1:1 为当前最优平衡点。
> 10k chunks 压测：P50 192.5ms / P95 296.4ms / P99 310.7ms。

**验收**
- 人工构造 30 条章节级 query，Recall@10 ≥ 0.8（基线以向量单路对比，证明混合检索有提升）。
- 1 万条证据规模下，检索 P95 ≤ 300ms（本地）。
- 关闭向量只留 BM25、关闭 BM25 只留向量，系统都能降级返回结果。

### P3 Agent 编排、Evidence Ledger 与冲突裁决（7 人日，核心阶段）

**目标**：产出“可解释”的研报，而不是一段流畅的文本。

**任务**
- [x] LangGraph 状态定义 + Postgres Checkpointer（进程重启可恢复）
- [x] 节点实现：
  - `Planner`：基于证据摘要生成章节大纲
  - `Wait_User` / `Human_Approval`：`interrupt` 暂停，等待前端确认或改稿
  - `Retriever`：按章节检索并组装上下文（动态上下文装配，控制 token）
  - `Critic`：检查证据是否支撑当前章节论点，不足则重试一次
  - `Writer`：基于证据写章节，要求 `[ev:id]` 引用
  - `Router`：按 `current_index` 路由到下一章节 / 裁决
- [x] 所有节点通过 `LLMClient` 角色接口调用，不直接依赖 DeepSeek/Qwen SDK；切换供应商不影响 LangGraph 编排
- [x] Claim 抽取：从生成文本中按句抽取 claim，强制绑定 `evidence_ids`
- [x] Claim 归一化：基于 qualifier（time/condition/scope）的 canonical key；冲突时不再合并
- [x] Evidence Ledger：`support / no_evidence` + 冲突后的 `rebut / mixed` 交叉证据条目
- [x] 裁决规则（确定性优先）：
  - 冲突类型：直接矛盾、数值不一致、时间差异、条件差异
  - 规则引擎输出冲突，LLM 只负责抽取与措辞，**不负责判定真假**
- [x] Evidence Guard：确定性校验每条引用
  - 证据 ID 必须存在于当前任务；无效引用直接剔除
  - claim 与证据文本相似度低于阈值 → `verified=false` + warning
- [x] SSE 事件协议：`state / token / citation / conflict / error / done`（progress/heartbeat 由 Java 层补）
- [x] HITL API：`POST /internal/tasks/{id}/plan` + `/resume`
- [x] 单测：裁决规则、Guard、HITL、Checkpointer 重启

> P3 当前实测（B站 100 秒视频，DeepSeek）：5 个章节，约 3.8k 字，38 条 claim，48 条 ledger，
> 41/41 引用校验通过，0 冲突（单视频）。多视频冲突面板与 SSE 待补。

**验收**
- 端到端产出 ≥ 3000 字研报，**100% 引用**具备合法 `evidence_id` 与时间戳。
- 在人工构造的“观点相反”视频对上，冲突面板至少检出 1 组真实冲突，且能展示双方证据。
- 生成中杀掉 Python 进程并重启，任务可从 Checkpointer 恢复（允许重跑当前节点）。
- 关闭 LLM 时返回明确错误事件，不产生半截脏数据。

### P4 Java 治理层（5 人日）

**目标**：让 Python 变成可随意崩溃的无状态执行器，Java 独自扛住前端。

**任务**
- [x] 任务表与状态机：合法迁移白名单、乐观锁 `version`、非法迁移直接拒绝
- [x] JDK 21 虚拟线程：`Executors.newVirtualThreadPerTaskExecutor()` 承载异步调度
- [x] SSE Hub：
  - Emitter 注册/注销、按 `taskId` 广播
  - 15s 心跳、`Last-Event-ID` 断线重放（最近 N 条事件）
  - 慢消费者清理
- [x] 异步调度：提交后立即返回，虚拟线程调用 Python；409 视为幂等接受
- [x] 回调接口：Python → Java，HMAC 签名 + `task_callbacks` 幂等
- [x] 容灾：Resilience4j 熔断 + Retry（执行层调用）
- [x] JWT 鉴权 + 单用户最多 3 个活跃任务
- [x] 可观测：Actuator + Hikari，健康检查可用

> P4 当前实测：Java `:8081` 创建任务 → 虚拟线程调用 Python 解析 → Python HMAC 回调 3 次（202）
> → Java SSE 收到 `state / parse_started / video_parsed / parse_finished`，任务进入 `PLANNING`。

**验收**
- [x] 500 并发 SSE 快速验证（21s，426MiB，健康）；10 分钟 soak / 连接泄漏统计待补。
- [x] 生成过程中杀掉 Python：SSE 不断开，收到 `EXECUTOR_UNAVAILABLE` 降级事件，任务进入 `FAILED` 可重试状态。
- [x] 重复发送同一回调 3 次，`task_callbacks` 仅 1 条（幂等生效）。
- [x] 非法状态迁移（如 `DONE → PARSING`）被拒绝（状态机单测）。

## 六、里程碑检查点

| 检查点 | 时点 | 必须成立 |

## 七、两种排期与压缩方案

### 方案 A：标准 6 周（推荐，简历主项目）

- 第 1 周：P0 + P1（解析链路打通）
- 第 2 周：P2 + P3 前半（检索 + Planner/HITL）
- 第 3 周：P3 后半（Ledger + 裁决 + Guard）
- 第 4 周：P4（Java 治理层）
- 第 5 周：P5（前端工作台）
- 第 6 周：P6（评测 + 包装 + 补漏）

### 方案 B：3 周压缩（先有 Demo，再补叙事）

- 第 1 周：P0 + P1 + P2，Python 单栈，状态存内存/Postgres
- 第 2 周：P3 核心（Planner/Writer/引用/冲突），前端只做最小双栏
- 第 3 周：P4 只做“任务表 + SSE Hub + 回调”三件事，P6 只做 3 个指标

**压缩时明确砍掉**：RAPTOR 多层树、完整鉴权与额度、B站播放器精确 seek（改本地视频）、复杂压测（改用 100 并发）。

### 方案 C：Java 优先（面试侧重治理层时）

P0 → P4（先做薄治理 + Mock Python）→ P1 → P2 → P3 → P5 → P6。
好处是早期就能讲“虚拟线程 + SSE + 状态机”，坏处是 AI 主线后置，Demo 风险高。

# 混合检索调优记录（P2 / P2.5）

> 记录 Gether 混合检索的测试方法、三轮调参过程、指标对比与最终结论。
> 相关阶段：P2（分块 / Embedding / pgvector / BM25 / RRF）、P2.5（过滤 / 30 query / 10k 压测）。
> 数据与结果可复现：`eval/datasets/`、`eval/results/`。

---

## 一、目标与约束

### 1.1 目标

在“多视频 → 证据切片”之后，把证据变成可检索的上下文块，并验证：

1. 混合检索是否优于向量单路与 BM25 单路；
2. 分块大小、RRF 参数、两路权重如何影响 Recall / nDCG / MRR；
3. 10k 分块规模下 P95 是否可接受；
4. 检索是否支持 `video_id / modality / 时间范围` 过滤。

### 1.2 约束

- 本地环境，无外部向量数据库；使用 PostgreSQL + pgvector。
- 本地 Embedding 选 `BAAI/bge-small-zh-v1.5`（512 维，FastEmbed ONNX），避免 bge-m3 的体积与首载延迟。
- 评测集来自单一长视频，query 为人工构造，存在过拟合风险；结论需在更多视频上复核。
- 相关性标签基于短语命中，而非逐条人工标注；指标用于相对比较，不宣称绝对水平。

## 二、数据与评测集

| 项 | 值 |
|---|---|

| 证据版本 | v2（medium GPU + LLM 纠错 + OCR/ASR 融合） |
| 证据数 | 369 条 |
| 模态 | OCR 221 / ASR 148 |
| 证据时长 | 约 19 分 35 秒 |
| 证据文件 | `data/output_v2/bilibili/BV1gehE6DEJ8/evidence.json` |

### 2.2 查询集

| 项 | 值 |
|---|---|
| 查询数 | **30** |
| 文件 | `eval/datasets/BV1gehE6DEJ8_queries.json` |
| 相关性 | `relevant_phrases` 任一命中 chunk 文本即视为相关 |
| 类型 | 事实型、比较型、观点型、时间线型、项目细节型 |

查询覆盖的主题：

- 离职与城市迁移（重庆 → 杭州）
- 租房：房租、隔断房、临安、通勤、整租
- 实习项目：摄像头报警、智能体、多租户、向量库
- 面试：被问穿、真实用户、上线、简历包装
- 求职：投递比例、第一周、大厂/小厂、RAG 评估集

> 查询示例：`杭州的房租为什么贵`、`摄像头报警项目怎么工作`、`为什么面试容易被问穿`、`投简历的面试邀约比例`。

### 2.3 指标定义

| 指标 | 定义 |
|---|---|
| `Hit@10` | Top-10 中至少命中 1 个相关 chunk 的 query 比例 |
| `Recall@10` | Top-10 命中的相关 chunk 数 / 该 query 全部相关 chunk 数，再对 query 取平均 |
| `MRR` | 第一个相关 chunk 排名倒数的平均值 |
| `nDCG@10` | 二值相关性下的归一化折损累计增益，越靠前命中越高 |

主排序依据：`Recall@10` → `nDCG@10` → `MRR`。  
选型时同时考虑引用粒度：块越大，recall 可能越高，但排序质量和时间定位会下降。

## 四、调参过程

### 4.1 第一轮：粗粒度分块与单路对照

搜索空间：

- 分块：220/320/60、360/500/80、500/700/100
- 权重：向量单路、BM25 单路、1:1、1.5:1、1:0.5、0.5:1、1:1.5
- `candidate_k`：20 / 50 / 100
- `rrf_k`：20 / 40 / 60 / 80

结果（每个分块取最佳组合）：

| 分块（target/max/overlap） | chunks | Recall@10 | nDCG@10 | MRR | 最佳组合 |
|---|---:|---:|---:|---:|---|
| 220 / 320 / 60 | 30 | 0.8671 | 0.8007 | 0.8756 | 1:1.5，cand 50，rrf 80 |
| **360 / 500 / 80** | 18 | **0.9284** | **0.8673** | **0.8931** | 1:1，cand 20，rrf 40 |
| 500 / 700 / 100 | 13 | 0.9802 | 0.8341 | 0.8353 | vector-only，cand 20，rrf 20 |

结论：

- 分块越大，Recall 越高（相关短语更容易被包进同一个块），但 nDCG/MRR 下降。
- 360 字符在召回与排序质量之间最平衡。
- 500 字符的 recall 接近 0.98，但一个块覆盖近 90 秒，引用粒度过粗。

### 4.2 单路 vs 混合（360 分块）

| 方案 | Recall@10 | nDCG@10 | MRR |
|---|---:|---:|---:|
| 向量单路 | 0.9110 | 0.8090 | 0.8236 |
| BM25 单路 | 0.8915 | 0.7930 | 0.8250 |
| **混合 1:1** | **0.9284** | **0.8673** | **0.8931** |

结论：混合检索在 nDCG 上明显优于两路单路，说明 RRF 不是“1+1 一定更好”，但在这个语料上确实有效。

### 4.3 第二轮：围绕 360 细化

搜索空间：

- 分块：280/400/60、360/480/60、400/540/80、460/620/80
- 权重：0.8:1 ~ 1.5:1
- `candidate_k`：15 / 20 / 30 / 50
- `rrf_k`：10 / 20 / 30 / 40 / 60

每个分块的最佳结果：

| 分块 | chunks | Recall@10 | nDCG@10 | MRR | 最佳组合 |
|---|---:|---:|---:|---:|---|
| 280 / 400 / 60 | 23 | 0.9263 | 0.8258 | 0.8542 | 1:1.2，cand 20，rrf 60 |
| **360 / 480 / 60** | 18 | **0.9368** | **0.8714** | **0.8931** | 1:1，cand 15，rrf 40 |
| 400 / 540 / 80 | 16 | 0.9463 | 0.8623 | 0.8678 | 0.8:1，cand 15，rrf 10 |
| 460 / 620 / 80 | 14 | 0.9405 | 0.8661 | 0.9000 | 1:1，cand 15，rrf 10 |

结论：

- 360/480/60 仍是最佳平衡点。
- `candidate_k=15` 在只有 18 个 chunk 的语料上表现略好，因为它排除了尾部噪声；但这不是可泛化的结论。
- 400/460 分块 recall 更高，但 nDCG/MRR 不如 360。

### 4.4 第三轮：360 附近微调

搜索空间：

- 分块：330/440/60、360/480/60、390/520/70
- 权重：0.9:1、1:1、1.1:1
- `candidate_k`：20 / 50
- `rrf_k`：20 / 30 / 40 / 50 / 60

| 分块 | chunks | Recall@10 | nDCG@10 | MRR | 最佳组合 |
|---|---:|---:|---:|---:|---|
| 330 / 440 / 60 | 19 | 0.9061 | 0.8234 | 0.8650 | 0.9:1，cand 20，rrf 40 |
| **360 / 480 / 60** | 18 | **0.9284** | **0.8674** | **0.8931** | 1.1:1，cand 20，rrf 30 |
| 390 / 520 / 70 | 17 | 0.9189 | 0.8532 | 0.9159 | 1.1:1，cand 20，rrf 60 |

结论：第三轮没有推翻 360；1.1:1 与 1:1 的差距极小，选择更简单、更容易解释的 1:1。

## 五、最终配置与指标

### 5.1 最终配置

```text
chunk_target_chars   = 360
chunk_max_chars      = 480
chunk_overlap_chars  = 60
candidate_k          = 50
rrf_k                = 40
vector_weight        = 1.0
bm25_weight          = 1.0
top_k                = 10
```

`candidate_k=50` 的选择说明：

- 在 18 个 chunk 的评测集上，`candidate_k=15` 的 nDCG 略高（0.8714 vs 0.8673）；
- 但 10k 规模下需要足够候选，否则 RRF 的互补性会被截断；
- 因此最终选择 50，接受约 0.004 的 nDCG 回退，换取可扩展性。

### 5.2 最终指标（30 query）

| 方案 | Recall@10 | nDCG@10 | MRR |
|---|---:|---:|---:|
| **混合检索（最终）** | **0.9284** | **0.8673** | **0.8931** |
| 向量单路 | 0.9110 | 0.8090 | 0.8236 |
| BM25 单路 | 0.8915 | 0.7930 | 0.8250 |

提升幅度：

| 对比 | Recall@10 | nDCG@10 | MRR |
|---|---:|---:|---:|
| 混合 vs 向量单路 | +1.9% | **+7.2%** | +8.4% |
| 混合 vs BM25 单路 | +4.1% | **+9.4%** | +8.3% |

### 5.3 结果解读

- 向量路负责语义泛化，BM25 负责专有名词/数字/精确短语；
- RRF 对两路排名做互补，不依赖分数尺度；
- 在该语料上，BM25 单独已经很强（大量重复词与口语短句），但混合仍稳定提升排序质量；
- 分块是最大的杠杆：块太大提升 recall、伤害 nDCG 和时间定位，块太小则上下文不足。

## 六、过滤能力

### 6.1 API 参数

```json
{
  "task_id": "...",
  "query": "杭州房租为什么高",
  "video_id": "...",
  "modalities": ["asr"],
  "time_start_ms": 90000,
  "time_end_ms": 130000,
  "top_k": 10
}
```

### 6.2 实现方式

- 向量路：SQL 动态 `WHERE`，过滤 `video_id`、`modalities &&`、时间区间重叠；
- BM25 路：先过滤 chunk 列表，再构建/检索；
- 无过滤时缓存 chunks + BM25，索引更新时失效。

### 6.3 测试

集成测试覆盖：

| 过滤 | 期望结果 |
|---|---|
| `modalities=["asr"]` | 命中 1 条 ASR 证据块 |
| `modalities=["ocr"]` | 0 条 |
| `time_start_ms=1500` | 1 条（块 1000–2000ms） |
| `time_start_ms=3000` | 0 条 |
| `time_end_ms=500` | 0 条 |
| 正确 `video_id` | 1 条 |
| 不存在的 `video_id` | 0 条 |

## 七、10k 分块延迟压测

### 7.1 测试设置

| 项 | 值 |
|---|---|
| 分块数 | 10,000 |
| 查询数 | 40 |
| Top-K | 10 |
| 向量维度 | 512 |
| 索引 | pgvector HNSW（cosine） |
| chunk 向量 | 随机归一化向量（只测延迟） |
| query 向量 | 真实 `bge-small-zh-v1.5` embedding |
| 索引构建耗时 | 47.9s |

### 7.2 结果

| 指标 | 值 |
|---|---:|
| P50 | 192.48ms |
| **P95** | **296.38ms** |
| P99 | 310.74ms |
| 平均 | 210.01ms |
| 最大 | 315.61ms |

### 7.3 解读与风险

- P95 已压到 300ms 以内，但余量很小；
- 延迟包含：query embedding + pgvector HNSW + BM25 命中 + RRF；
- chunk 向量随机生成，只验证检索链路延迟，不验证语义质量；
- 后续可优化：
  - HNSW `ef_search` / `m` 参数；
  - 降维或更小模型；
  - query embedding 缓存；
  - BM25 预计算/持久化；
  - 候选截断与批量查询。

## 八、过程中发现的问题

| # | 问题 | 原因 | 处理 |
|---:|---|---|---|
| 1 | BM25 召回为空 | 分词正则只匹配单个汉字，`杭州` 被切成 `杭` | 改为 `[\u4e00-\u9fff]+` |
| 2 | 小分块测试无法生效 | `target_chars` 被强制下限 80 | 下限改为 20 |
| 3 | 出现只含 overlap 的重复块 | flush 后 carry 又进入下一块 | 跳过 carry-only 块 |
| 4 | 小语料 BM25 分数为 0 | 只有 1 个 chunk 时 IDF=0 | 扩充评测语料；后续可评估 BM25+ |
| 5 | 自动索引失败 | `.env` 仍是 `BAAI/bge-m3`，FastEmbed 不支持 | 改为 `bge-small-zh-v1.5` |
| 6 | 解析后立刻查 chunks 为 0 | 后台索引与状态更新存在时间差 | 轮询 chunks 或等待索引完成 |
| 7 | 小语料 candidate_k 过拟合 | 15 个候选排除了尾部噪声 | 生产默认 50，记录 trade-off |
| 8 | 过滤查询 BM25 可能漏召回 | BM25 在全部 chunk 上取 Top-K 后再过滤会截断 | 先过滤再构建 BM25 |

## 九、结论

1. **混合检索有效**：在 30 条 query 上，nDCG@10 相对向量单路 +7.2%，相对 BM25 单路 +9.4%。
2. **分块是第一优先级**：360/480/60 是当前数据上的最佳平衡；大块的高 recall 不代表更好的 RAG 上下文。
3. **参数不宜过拟合小语料**：`candidate_k=15` 在 18 个 chunk 上略好，但最终选 50 以保证 10k 规模。
4. **P95 达标但余量小**：10k chunks 下 296ms；若要冲 200ms，需要 HNSW/模型/缓存层优化。
5. **过滤已可用**：`video_id / modality / 时间范围` 已接入，并有集成测试。
6. **RAPTOR 暂不做**：当前收益不确定，先保证 P3 主链路。
